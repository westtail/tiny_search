# tiny_search

Rubyで小さな検索エンジンを段階的に作りながら、Elasticsearch / Lucene の仕組みを理解する学習プロジェクト。

## 方針

- いきなり転置インデックスには行かず、全文スキャンから少しずつ進める
- 各ステップで「何が問題で、なぜこの変更で解決するか」をメモに残す（Zenn/Qiitaの記事にする）
- 最初は英語データで仕組みを作り、後のステップで日本語に対応する
- 依存は標準ライブラリのみ（Ruby 3.3）

## ステップ

| # | 内容 | 状態 |
|---|---|---|
| 1 | 全文スキャン（`include?` で総なめ） | 完了 |
| 2 | トークナイズ（単語単位で一致判定、複数語はAND） | 完了 |
| 3 | スコアリング（TFで並べる） | 未着手 |
| 4 | 計測（文書数を増やして遅くなるのを `Benchmark` で確認） | 未着手 |
| 5 | 転置インデックス（4と同じデータで速度比較） | 未着手 |
| 6 | TF-IDF → BM25 | 未着手 |
| 7 | 日本語（bigram）、永続化、HTTP化、gem化 | 未着手 |

## ファイル

- `docs.json` — テスト用の英語文書16件（`{id: {title, body}}`）
- `stepN_*.rb` — 各ステップの実装。`ruby step1_full_scan.rb ruby` のように実行
- `logs/stepN.log` — 各ステップの実行ログ（日時、Rubyバージョン、コマンドと出力）

## ステップ1のメモ

- 仕組み: 全文書を毎回頭から読み、クエリ文字列を含むか判定する
- 問題1: 部分一致なので単語の境界を無視する（`index` で `indexing` を含む文書1にもヒットする）
- 問題2: 当たり/外れだけで順位がつかない（`is` は16件中13件に当たるが、どれも同じ扱い）
- 問題3: 毎回全件を読むので文書が増えると遅くなる

## ステップ2のメモ

- 仕組み: `downcase.scan(/[a-z0-9]+/)` で単語に分け、単語単位で一致を判定する。複数語はAND
- 解決: 単語の境界を見るので、`index` が `indexing` に当たらなくなった（4件→3件）
- 新しい問題1: 語形の違いを区別してしまう。`search engine` は `search engines` の文書7を、`ruby gem` は `Ruby gems` の文書7を取りこぼす（ステップ1では部分一致で当たっていた）。Elasticsearchではアナライザのステミングで解決する部分
- 新しい問題2: `is` は13件のまま。13件とも本当に単語 `is` を含んでいるので一致判定としては正しいが、ありふれた語で、検索の役に立たない。ストップワード除去やIDF（ステップ6）で扱う
- 新しい問題3: `tf-idf` は `tf` と `idf` に分かれる。今はANDなので問題ないが、語順は見ていない（フレーズ検索は未対応）
- 残っている問題: 順位がつかない（ステップ3）、毎回全件をトークナイズするので遅い（ステップ4、5）
